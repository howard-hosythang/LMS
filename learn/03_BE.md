# 03. Backend - Học Và Nắm Library74 Từ Gốc

Tài liệu này xem bạn là người mới học lập trình web ở mức cơ bản. Mục tiêu không phải học thuộc code, mà là hiểu backend đang giải quyết vấn đề gì, vì sao chọn cách đó, và khi hội đồng hỏi thì bạn giải thích được bằng logic.

Lộ trình học toàn project:

1. FE - Frontend: người dùng nhìn thấy gì, bấm gì, dữ liệu đi đâu.
2. DB - Database: dữ liệu được lưu như thế nào.
3. BE - Backend: nghiệp vụ, bảo mật, API.
4. AI - Recommendation, semantic search, xử lý tri thức.
5. Deploy/DevOps - đưa hệ thống chạy thật trên server.

Trong file này ta học phần BE.

---

## 1. Backend Là Gì?

### 1.1. Vấn Đề Thực Tế

Frontend chỉ là giao diện chạy trên trình duyệt. Nếu chỉ có frontend thì người dùng có thể nhìn thấy nút, form, bảng dữ liệu, nhưng hệ thống chưa thật sự biết:

- Ai đang đăng nhập.
- Người này có quyền mượn sách hay không.
- Quyển sách còn bản sao khả dụng hay không.
- Khi trả trễ thì phạt bao nhiêu.
- Email xác thực gửi như thế nào.
- Dữ liệu phải lưu vào bảng nào.
- Khi thủ thư xử lý một yêu cầu hỗ trợ thì ai được thông báo.

Backend là phần xử lý những câu hỏi đó.

Nói đơn giản:

```text
Người dùng -> Frontend -> gọi API -> Backend -> Database / Kafka / AI / Email -> Backend trả kết quả -> Frontend hiển thị
```

### 1.2. Định Nghĩa

**Backend** là phần chạy trên server, chịu trách nhiệm:

- Nhận request từ frontend.
- Kiểm tra đăng nhập và phân quyền.
- Xử lý nghiệp vụ.
- Đọc/ghi database.
- Gọi hệ thống ngoài như AI, email, thanh toán.
- Trả response cho frontend.

Trong project Library74, backend nằm ở:

```text
LMS_BE/
```

Nếu frontend là quầy giao tiếp với người dùng, thì backend là bộ phận xử lý hồ sơ phía sau.

## 3. Backend Nhận Request Như Thế Nào?

### 3.1. HTTP Request Là Gì?

Khi frontend gọi API, trình duyệt gửi một HTTP request.

Ví dụ:

```text
GET /api/v1/contact-messages/my
Authorization: Bearer <access_token>
```

Ý nghĩa:

- `GET`: muốn lấy dữ liệu.
- `/api/v1/contact-messages/my`: đường dẫn API.
- `Authorization`: token chứng minh người dùng đã đăng nhập.

Backend xử lý xong sẽ trả HTTP response.

Ví dụ:

```json
{
  "code": 200,
  "message": "Success",
  "data": [...]
}
```

### 3.2. Các HTTP Method Hay Gặp

| Method | Ý nghĩa | Ví dụ trong Library74 |
|---|---|---|
| `GET` | Lấy dữ liệu | Lấy danh sách sách, lấy phiếu hỗ trợ |
| `POST` | Tạo mới hoặc thực hiện hành động | Đăng nhập, tạo yêu cầu mượn |
| `PUT` | Cập nhật toàn bộ | Cập nhật hồ sơ |
| `PATCH` | Cập nhật một phần | Đổi trạng thái phiếu hỗ trợ |
| `DELETE` | Xóa | Xóa wishlist item, hủy đặt trước |

Hội đồng có thể hỏi: "Vì sao không dùng toàn POST?"

Trả lời logic:

```text
Mỗi HTTP method thể hiện ý nghĩa khác nhau. GET dùng để đọc, POST dùng để tạo hoặc thực hiện hành động, PATCH dùng để cập nhật một phần. Việc dùng đúng method giúp API rõ nghĩa, dễ test và dễ bảo trì.
```

## 4. Spring Boot Là Gì?

### 4.1. Vấn Đề Thực Tế

Nếu tự viết server từ đầu, ta phải tự xử lý rất nhiều việc:

- Mở cổng 8080.
- Parse JSON request.
- Gọi đúng hàm theo URL.
- Kết nối database.
- Quản lý transaction.
- Bảo mật token.
- Trả lỗi chuẩn.

Spring Boot giúp làm sẵn phần khung đó.

### 4.2. Định Nghĩa

**Spring Boot** là framework Java giúp xây dựng ứng dụng backend nhanh hơn bằng cách cung cấp sẵn cấu hình và thư viện phổ biến.

Trong project, ứng dụng chính nằm ở module:

```text
LMS_BE/library-bootstrap/
```

Khi chạy backend, Spring Boot:

1. Đọc cấu hình trong `application.yml`.
2. Tạo các object cần thiết như Controller, Service, Repository.
3. Kết nối database, Kafka, mail.
4. Mở server HTTP ở cổng `8080`.
5. Nhận request từ frontend.

### 4.3. Annotation Là Gì?

Trong Java Spring, annotation là ký hiệu bắt đầu bằng `@`, dùng để nói với Spring một class hoặc method có vai trò gì.

Ví dụ:

```java
@RestController
@RequestMapping("/api/v1/contact-messages")
public class ContactMessageController {
}
```

Ý nghĩa:

- `@RestController`: class này là nơi nhận API request và trả JSON.
- `@RequestMapping`: tất cả API trong class này bắt đầu bằng `/api/v1/contact-messages`.

Không cần học thuộc tất cả annotation, chỉ cần hiểu chúng là cách "đánh dấu vai trò" cho Spring.

## 6. Luồng Cơ Bản: Controller -> Service/UseCase -> Repository -> Database

### 6.1. Tư Duy 4 Lớp

Một request backend thường đi qua các lớp:

```text
Controller -> UseCase/Service -> Repository -> Database
```

Ý nghĩa:

| Lớp | Làm gì |
|---|---|
| Controller | Nhận request, validate input, gọi use case |
| UseCase/Service | Xử lý nghiệp vụ |
| Repository | Đọc/ghi database |
| Entity | Đại diện bảng trong database |

### 6.2. Ví Dụ Dễ Hiểu

Người dùng bấm "Tạo phiếu hỗ trợ":

```text
Frontend gửi POST /api/v1/contact-messages
-> ContactMessageController nhận request
-> Kiểm tra người dùng đã đăng nhập
-> Tạo ticket code dạng REQ-...
-> Lưu vào bảng contact_messages
-> Gửi notification cho thủ thư/admin
-> Trả dữ liệu phiếu vừa tạo cho frontend
```

Người dùng không cần biết database có bảng gì. Frontend cũng không tự ghi database. Backend là nơi giữ luật nghiệp vụ.

### 6.3. Vì Sao Không Cho Frontend Gọi Thẳng Database?

Vì rất nguy hiểm:

- Lộ thông tin kết nối database.
- Người dùng có thể tự sửa dữ liệu.
- Không kiểm soát được quyền.
- Không kiểm tra được nghiệp vụ.

Trả lời hội đồng:

```text
Frontend không được truy cập database trực tiếp vì trình duyệt là môi trường không tin cậy. Backend đứng giữa để xác thực, phân quyền, validate dữ liệu và bảo vệ database.
```

### 7.1. Vấn Đề Thực Tế

Controller chính là nơi định nghĩa các địa chỉ API đó.

### 7.2. Controller Trong Project

Một số controller quan trọng:

```text
library-auth-module/.../AuthController.java
```

### 7.3. Controller Nên Làm Gì Và Không Nên Làm Gì?

Controller nên:

- Nhận request.
- Kiểm tra input cơ bản bằng validation.
- Lấy thông tin user hiện tại nếu cần.

- Chứa quá nhiều logic nghiệp vụ phức tạp.
- Tự viết nhiều câu SQL nếu có thể tách ra service/repository.
- Tự quyết định tất cả trạng thái nghiệp vụ.

## 8. DTO, Request, Response Là Gì?

### 8.1. Vấn Đề Thực Tế

Database có thể có rất nhiều field nhạy cảm:

- `hashed_password`
- `provider_id`
- token
- thông tin nội bộ

Không thể trả nguyên Entity database ra frontend.

### 8.2. Định Nghĩa

**DTO** là object dùng để truyền dữ liệu giữa frontend và backend.

Có 2 loại thường gặp:

- Request DTO: dữ liệu frontend gửi lên.
- Response DTO: dữ liệu backend trả về.

Ví dụ trong contact:

```text
SubmitContactMessageRequest
ContactMessageResponse
ContactMessageCommentResponse
```

Ý nghĩa:

- Request chỉ nhận các field cần thiết như subject, message, category.
- Response chỉ trả những field frontend cần hiển thị.

Trả lời hội đồng:

```text
DTO giúp tách dữ liệu API khỏi Entity database. Nhờ vậy backend kiểm soát được field nào được nhận, field nào được trả về, tránh lộ dữ liệu nhạy cảm và giúp API ổn định hơn khi database thay đổi.
```

## 9. Validation Là Gì?

### 9.1. Vấn Đề Thực Tế

Người dùng có thể gửi dữ liệu sai:

- Email sai định dạng.
- Subject quá dài.
- Rating ngoài khoảng 1 đến 5.
- Message rỗng.
- Status không thuộc enum cho phép.

Frontend có thể validate trước, nhưng backend vẫn phải validate lại vì request có thể bị gửi bằng Postman/curl.

### 9.2. Validation Trong Project

Ví dụ trong `ContactMessageController`:

```java
@NotBlank
@Size(max = 200)
String subject
```

Ý nghĩa:

- `@NotBlank`: không được rỗng.
- `@Size(max = 200)`: tối đa 200 ký tự.

Ví dụ status:

```java
@Pattern(regexp = "NEW|IN_PROGRESS|RESOLVED|CLOSED")
String status
```

Ý nghĩa: chỉ cho phép các trạng thái hợp lệ.

Trả lời hội đồng:

```text
Backend validate để bảo vệ hệ thống khỏi dữ liệu sai hoặc request giả mạo. Frontend validate giúp trải nghiệm tốt hơn, còn backend validate là lớp bảo vệ bắt buộc.
```

## 10. Database Và Entity

### 10.1. Entity Là Gì?

**Entity** là class Java đại diện cho một bảng trong database.

Ví dụ:

```text
UserEntity -> bảng users
PublicationEntity -> bảng publications
ItemEntity -> bảng items
BorrowingTransactionEntity -> bảng borrowing_transactions
FineEntity -> bảng fines
ReservationEntity -> bảng reservations
RatingEntity -> bảng ratings
```

Entity giúp Java làm việc với dữ liệu dưới dạng object thay vì chỉ là dòng/cột SQL.

### 10.2. Những Nhóm Bảng Chính

| Nhóm | Bảng tiêu biểu | Ý nghĩa |
|---|---|---|
| User/Auth | `users`, `roles`, `user_roles`, `refresh_tokens` | Tài khoản và phân quyền |
| Catalog | `publications`, `items`, `authors`, `categories`, `tags` | Dữ liệu sách |
| Circulation | `borrowing_transactions`, `reservations`, `fines` | Mượn trả, đặt trước, phạt |
| Recommendation | `ratings`, `wishlists`, `search_history` | Cá nhân hóa và tương tác |
| Contact | `contact_messages`, `contact_message_comments`, `contact_internal_notes` | Hỗ trợ người dùng |
| Technical | `flyway_schema_history` | Theo dõi migration database |

### 10.3. Publication Và Item Khác Nhau Thế Nào?

Đây là câu rất hay bị hỏi.

```text
Publication = đầu sách / metadata sách
Item = bản sao cụ thể có thể mượn
```

Ví dụ thư viện có sách "Clean Code".

- `Publication`: Clean Code, tác giả, ISBN, mô tả, ảnh bìa.
- `Item`: bản sao barcode `BC001`, `BC002`, `BC003`.

Một publication có nhiều item.

Trả lời hội đồng:

```text
Em tách publication và item vì một đầu sách có thể có nhiều bản sao. Người dùng tìm kiếm theo publication, nhưng khi mượn thì hệ thống phải chọn một item cụ thể để theo dõi trạng thái AVAILABLE, BORROWED, RESERVED hoặc LOST.
```

## 13. Transaction Là Gì?

### 13.1. Vấn Đề Thực Tế

Một nghiệp vụ có thể cần cập nhật nhiều bảng cùng lúc.

Ví dụ trả sách:

- Cập nhật transaction thành `RETURNED`.
- Cập nhật item thành `AVAILABLE`.
- Nếu trễ hạn thì tạo fine.
- Có thể gửi notification.

Nếu cập nhật transaction xong nhưng cập nhật item fail, dữ liệu sẽ sai.

### 13.2. Định Nghĩa

**Transaction** là cơ chế đảm bảo một nhóm thao tác database hoặc thành công hết, hoặc thất bại thì rollback hết.

Trong Spring, thường dùng:

```java
@Transactional
```

Ý nghĩa:

```text
Nếu một bước trong nghiệp vụ lỗi, database quay lại trạng thái trước đó.
```

Trả lời hội đồng:

```text
Transaction giúp đảm bảo tính nhất quán dữ liệu. Với nghiệp vụ mượn trả, một hành động có thể ảnh hưởng nhiều bảng, nên cần transaction để tránh trạng thái nửa thành công nửa thất bại.
```

## 14. Flyway Là Gì?

### 14.1. Vấn Đề Thực Tế

Database thay đổi theo thời gian:

- Thêm bảng contact.
- Thêm cột `librarian_campus`.
- Thêm index tìm kiếm.
- Seed dữ liệu demo.

Nếu mỗi người tự sửa database bằng tay thì môi trường local, test, production sẽ lệch nhau.

### 14.2. Định Nghĩa

**Flyway** là công cụ quản lý version database bằng file migration SQL.

Trong project, migration nằm ở:

```text
LMS_BE/library-bootstrap/src/main/resources/db/migration/
```

Ví dụ:

## 15. Authentication Và Authorization

### 15.1. Authentication Là Gì?

**Authentication** là xác thực danh tính: "Bạn là ai?"

Ví dụ:

- Đăng nhập bằng email/password.
- Đăng nhập bằng Google OAuth2.
- Verify email.
- Refresh access token.

Module liên quan:

```text
library-auth-module/
```

### 15.2. Authorization Là Gì?

**Authorization** là phân quyền: "Bạn được làm gì?"

Ví dụ:

- Student được xem sách, mượn sách, xem phiếu hỗ trợ của mình.
- Librarian được xử lý mượn trả, quản lý bản sao, xử lý contact inbox.
- Admin được quản lý tài khoản, role, audit.

### 15.3. JWT Là Gì?

**JWT** là token backend cấp sau khi đăng nhập. Frontend lưu token và gửi kèm mỗi request.

Luồng:

```text
User login -> Backend kiểm tra password -> Backend cấp access token -> Frontend gọi API kèm Bearer token -> Backend xác minh token
```

### 15.4. Vì Sao Cần Refresh Token?

Access token nên sống ngắn để giảm rủi ro nếu bị lộ. Refresh token dùng để lấy access token mới mà không bắt user đăng nhập lại liên tục.

Trả lời hội đồng:

```text
Access token dùng cho request hằng ngày và nên hết hạn nhanh. Refresh token sống lâu hơn để cấp access token mới. Cách này cân bằng giữa bảo mật và trải nghiệm người dùng.
```

## 19. Circulation: Mượn, Trả, Đặt Trước, Phí Phạt

### 19.1. Circulation Là Gì?

Circulation là nghiệp vụ vận hành thư viện:

### 19.3. Luồng Mượn Sách

```text
Student bấm mượn
```


Trả lời hội đồng:

```text
Mượn trả là nghiệp vụ cần tính nhất quán cao, vì nó ảnh hưởng cùng lúc đến transaction, item và fine. Backend xử lý tập trung để tránh việc một bản sao bị mượn trùng hoặc trạng thái sai.
```

Trả lời hội đồng:

```text
Kafka giúp backend xử lý bất đồng bộ. Những việc không cần trả kết quả ngay như gửi email hoặc notification có thể đưa vào queue, giúp request chính nhẹ hơn và hệ thống dễ mở rộng.
```

## 32. Những Câu Hội Đồng Hay Hỏi

### Câu 1: Vì sao cần backend khi đã có frontend?

Trả lời:

```text
Frontend chỉ chạy trên trình duyệt và không đáng tin cậy để giữ nghiệp vụ hoặc secret. Backend xử lý đăng nhập, phân quyền, nghiệp vụ, database và tích hợp hệ thống ngoài. Nếu không có backend, dữ liệu và bảo mật sẽ không được kiểm soát.
```

### Câu 2: Vì sao dùng Spring Boot?

Trả lời:

```text
Spring Boot cung cấp sẵn nền tảng cho REST API, dependency injection, security, database, transaction và cấu hình. Với hệ thống nhiều nghiệp vụ như thư viện, Spring Boot giúp backend có cấu trúc rõ và dễ mở rộng.
```

### Câu 3: Vì sao chia multi-module?

Trả lời:

```text
Project chia module theo nghiệp vụ: auth, user, catalog, circulation, recommendation. Cách này giúp mỗi phần có trách nhiệm rõ, giảm code lẫn lộn và dễ bảo trì hơn khi hệ thống lớn.
```

### Câu 4: Controller khác Service khác Repository thế nào?

Trả lời:

```text
Controller nhận request và trả response. Service hoặc UseCase xử lý nghiệp vụ. Repository làm việc với database. Tách như vậy giúp code rõ trách nhiệm và dễ test.
```

### Câu 5: Vì sao dùng Flyway?

Trả lời:

```text
Flyway quản lý schema database bằng migration có version. Nhờ vậy local, test và production chạy cùng một lịch sử thay đổi database, tránh sửa tay gây lệch môi trường.
```

### Câu 6: JWT dùng để làm gì?

Trả lời:

```text
JWT là token chứng minh người dùng đã đăng nhập. Frontend gửi token trong header, backend kiểm tra token để biết user là ai và có role gì trước khi cho gọi API.
```

### Câu 7: Vì sao không chỉ ẩn nút trên frontend để bảo mật?

Trả lời:

```text
Ẩn nút chỉ cải thiện giao diện, không phải bảo mật. Người dùng vẫn có thể gọi API trực tiếp bằng công cụ ngoài. Vì vậy backend phải kiểm tra token và role cho từng API quan trọng.
```

### Câu 8: Vì sao publication và item tách riêng?

Trả lời:

```text
Publication là đầu sách, còn item là từng bản sao cụ thể. Một đầu sách có thể có nhiều bản sao, mỗi bản sao có barcode và trạng thái riêng. Tách như vậy giúp quản lý mượn trả chính xác.
```

### Câu 9: Kafka dùng để làm gì?

Trả lời:

```text
Kafka dùng để xử lý bất đồng bộ các event như gửi email và notification. Request chính không bị phụ thuộc trực tiếp vào thời gian gửi email, giúp hệ thống phản hồi nhanh và dễ mở rộng.
```

### Câu 10: Backend liên kết AI như thế nào?

Trả lời:

```text
Backend không trực tiếp chạy model AI. Backend nhận request từ frontend, kiểm tra quyền và gọi AI service qua AI Gateway. AI service xử lý semantic search/recommendation rồi trả kết quả hoặc callback về backend.
```

## 34. Bản Tóm Tắt Một Phút

Nếu phải giải thích backend Library74 trong một phút:

```text
Backend Library74 là hệ thống Spring Boot Java 21 chạy trên server, chịu trách nhiệm xử lý nghiệp vụ thư viện, bảo mật và dữ liệu. Frontend chỉ gửi request, còn backend kiểm tra token JWT, phân quyền theo role STUDENT/LIBRARIAN/ADMIN, validate input, xử lý nghiệp vụ và lưu PostgreSQL.
```
