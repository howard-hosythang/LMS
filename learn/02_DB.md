# 02. Database - Học Và Nắm Library74 Từ Gốc

Tài liệu này xem bạn là người mới học lập trình web ở mức cơ bản. Mục tiêu không phải học thuộc bảng, mà là hiểu database đang giải quyết vấn đề gì, vì sao thiết kế như vậy, và khi hội đồng hỏi thì bạn giải thích được bằng logic.

Lộ trình học toàn project:

1. FE - Frontend: người dùng nhìn thấy gì, bấm gì, dữ liệu đi đâu.
2. DB - Database: dữ liệu được lưu như thế nào.
3. BE - Backend: nghiệp vụ, bảo mật, API.
4. AI - Recommendation, semantic search, xử lý tri thức.
5. Deploy/DevOps - đưa hệ thống chạy thật trên server.

Trong file này ta học phần Database.

## 1. Database Là Gì?

### 1.1. Vấn Đề Thực Tế

Một hệ thống thư viện cần nhớ rất nhiều thứ:

- Ai là sinh viên, thủ thư, admin.
- Sách nào đang có trong thư viện.
- Mỗi sách có bao nhiêu bản sao.
- Bản sao nào đang được mượn.
- Ai đang mượn sách nào.
- Khi nào đến hạn trả.
- Ai bị phạt, phạt bao nhiêu.
- Người dùng đã wishlist, rating, tìm kiếm gì.
- Phiếu hỗ trợ đang ở trạng thái nào.
- Vector AI của sách nằm ở đâu.

Nếu chỉ lưu trong frontend hoặc biến tạm thời của backend, khi tắt app dữ liệu sẽ mất.

Database là nơi lưu dữ liệu lâu dài.

Nói đơn giản:

```text
Frontend -> Backend -> Database
```

Frontend không chạm trực tiếp vào database. Backend là người kiểm soát việc đọc/ghi.

### 1.2. Định Nghĩa

**Database** là hệ thống lưu trữ dữ liệu có cấu trúc, cho phép thêm, đọc, sửa, xóa và truy vấn dữ liệu.

Trong Library74, database chính là:

```text
PostgreSQL + pgvector
```

---

## 2. Vì Sao Dùng PostgreSQL?

PostgreSQL là hệ quản trị cơ sở dữ liệu quan hệ mạnh và phổ biến.

Project dùng PostgreSQL vì:

- Lưu dữ liệu quan hệ tốt: user, sách, bản sao, giao dịch.
- Hỗ trợ transaction để dữ liệu nhất quán.
- Hỗ trợ constraint như khóa chính, khóa ngoại, unique.
- Hỗ trợ index để truy vấn nhanh.
- Hỗ trợ JSONB cho dữ liệu linh hoạt.
- Có extension `pgvector` để lưu vector AI.

Trả lời hội đồng:

```text
PostgreSQL phù hợp vì hệ thống thư viện có nhiều quan hệ dữ liệu chặt chẽ như user, sách, bản sao, giao dịch mượn và phí phạt. Ngoài ra PostgreSQL hỗ trợ pgvector, giúp lưu embedding AI ngay trong cùng hệ thống database.
```

## 3. Table, Row, Column Là Gì?

### 3.1. Table

**Table** là bảng lưu một loại dữ liệu.

Ví dụ:

```text
users
publications
items
borrowing_transactions
fines
contact_messages
```

### 3.2. Row

**Row** là một dòng dữ liệu cụ thể.

Ví dụ một dòng trong bảng `users` là một người dùng.

### 3.3. Column

**Column** là một thuộc tính.

Ví dụ bảng `users` có các cột:

```text
id
email
full_name
hashed_password
status
created_at
updated_at
```

Ví dụ dễ hiểu:

```text
Table users
-> mỗi row là một tài khoản
-> mỗi column là một thông tin của tài khoản
```

## 4. Primary Key Là Gì?

### 4.1. Vấn Đề Thực Tế

Trong thư viện có thể có nhiều người tên giống nhau.

Ví dụ:

```text
Nguyễn Văn A
Nguyễn Văn A
```

Nếu chỉ dựa vào tên, hệ thống không biết ai là ai.

### 4.2. Định Nghĩa

**Primary Key**, viết tắt là `PK`, là khóa chính dùng để định danh duy nhất một dòng trong bảng.

Ví dụ:

```text
users.id
publications.id
items.id
borrowing_transactions.id
```

Khi nói `user_id = 15`, database biết chính xác đó là user nào.

Trả lời hội đồng:

```text
Primary key giúp định danh duy nhất mỗi bản ghi. Trong hệ thống có thể có nhiều tên trùng nhau, nhưng id thì không trùng, nên backend dùng id để liên kết dữ liệu chính xác.
```

---

## 5. Foreign Key Là Gì?

### 5.1. Vấn Đề Thực Tế

Một giao dịch mượn sách cần biết:

- Ai mượn.
- Mượn bản sao nào.

Ta không nên copy toàn bộ thông tin user và item vào transaction. Ta chỉ cần lưu id tham chiếu.

### 5.2. Định Nghĩa

**Foreign Key**, viết tắt là `FK`, là khóa ngoại dùng để liên kết một bảng với bảng khác.

Ví dụ:

```text
borrowing_transactions.user_id -> users.id
borrowing_transactions.item_id -> items.id
items.publication_id -> publications.id
```

Ý nghĩa:

- Transaction biết user nào mượn.
- Transaction biết item nào được mượn.
- Item biết nó thuộc đầu sách nào.

Trả lời hội đồng:

```text
Foreign key giúp database đảm bảo dữ liệu liên kết hợp lệ. Ví dụ một transaction không được tham chiếu tới user không tồn tại hoặc item không tồn tại.
```

## 6. Unique, NOT NULL, CHECK Là Gì?

Database không chỉ lưu dữ liệu, mà còn bảo vệ dữ liệu.

### 6.1. Unique

`UNIQUE` đảm bảo giá trị không bị trùng.

Ví dụ:

```text
users.email
items.barcode
publications.isbn
roles.role_name
```

Ý nghĩa:

- Một email không thể đăng ký hai tài khoản.
- Một barcode không thể đại diện hai bản sao.

### 6.2. NOT NULL

`NOT NULL` nghĩa là bắt buộc có dữ liệu.

Ví dụ:

```text
users.email
users.full_name
items.barcode
items.publication_id
```

### 6.3. CHECK

`CHECK` giới hạn giá trị hợp lệ.

Ví dụ status user chỉ nên là:

```text
ACTIVE
INACTIVE
LOCKED
BANNED
```

Item status chỉ nên là:

```text
AVAILABLE
BORROWED
RESERVED
IN_MAINTENANCE
LOST
```

Trả lời hội đồng:

```text
Constraint giúp database tự bảo vệ tính đúng đắn dữ liệu. Backend có validate, nhưng database vẫn cần ràng buộc cuối cùng để tránh dữ liệu sai lọt vào.
```

## 7. Quan Hệ 1-1, 1-N, N-N

### 7.1. Quan Hệ 1-N

Một user có nhiều giao dịch mượn.

```text
users 1 -> N borrowing_transactions
```

Một publication có nhiều item.

```text
publications 1 -> N items
```

### 7.2. Quan Hệ N-N

Một sách có nhiều tác giả, một tác giả có nhiều sách.

```text
publications N -> N authors
```

Database không lưu N-N trực tiếp. Nó dùng bảng nối:

```text
publication_authors
```

Tương tự:

```text
publication_categories
publication_tags
user_roles
fine_payment_order_fines
```

### 7.3. Quan Hệ 0..1

Một user thường có tối đa một wishlist.

```text
users 0..1 -> 0..1 wish_lists
```

Trả lời hội đồng:

```text
Quan hệ giúp mô hình hóa thế giới thật. Ví dụ một đầu sách có nhiều bản sao là 1-N, còn sách và tác giả là N-N nên cần bảng nối để tránh lặp dữ liệu và quản lý quan hệ rõ ràng.
```

## 8. ERD Là Gì?

**ERD** là Entity Relationship Diagram, sơ đồ mô tả các bảng và quan hệ giữa bảng.

Trong project có tài liệu:

```text
LMS_BE/ERD_SPECIFICATION.md
```

Khi nhìn ERD, bạn cần đọc được:

- Bảng nào là thực thể chính.
- Bảng nào là bảng nối.
- Cột nào là khóa chính.
- Cột nào là khóa ngoại.
- Quan hệ là 1-N hay N-N.

Trả lời hội đồng:

```text
ERD giúp trình bày cấu trúc dữ liệu tổng thể. Thay vì chỉ xem code, hội đồng có thể nhìn ERD để hiểu user, sách, mượn trả, phí phạt và AI liên kết với nhau như thế nào.
```

## 10. Nhóm User Và Role

### 10.1. Bảng `users`

`users` là bảng trung tâm cho tài khoản.

Nó lưu:

- Email.
- Mật khẩu đã hash.


Một user có thể có nhiều role, một role thuộc nhiều user.

Vì vậy cần bảng nối:

```text
user_roles(user_id, role_id)
```

Trả lời hội đồng:

```text
Project tách user và role để phân quyền linh hoạt. User không lưu role bằng text đơn giản, mà liên kết qua user_roles để có thể mở rộng nếu một tài khoản cần nhiều vai trò.
```

## 11. Vì Sao `hashed_password` Có Thể Nullable?

Một số user đăng nhập bằng Google OAuth2.

Với OAuth:

- User không đặt password trong hệ thống.
- Backend nhận danh tính từ Google.
- Vì vậy `hashed_password` có thể null.

Trả lời hội đồng:

```text
hashed_password nullable vì hệ thống hỗ trợ OAuth. Tài khoản đăng nhập bằng Google không cần lưu password nội bộ, nhưng vẫn có user record để phân quyền và liên kết dữ liệu.
```

## 12. Nhóm Catalog: Sách Và Bản Sao

### 12.1. `publications`

`publications` là đầu sách hoặc metadata sách.

Nó lưu:

- Title.
- ISBN.
- Mô tả.
- Năm xuất bản.
- Ngôn ngữ.
- Ảnh bìa.
- URL PDF.
- AI summary.
- AI target audience.

### 12.2. `items`

`items` là bản sao cụ thể có thể mượn.

Nó lưu:

- Barcode.
- Publication id.
- Status.
- Condition.
- Branch.
- Location.

### 12.3. Vì Sao Tách Publication Và Item?

Ví dụ thư viện có sách "Clean Code".

```text
Publication: Clean Code
Item 1: barcode CC001, AVAILABLE
Item 2: barcode CC002, BORROWED
Item 3: barcode CC003, LOST
```

Nếu gộp chung, rất khó biết mỗi bản sao đang ở đâu và trạng thái gì.

Trả lời hội đồng:

```text
Publication là đầu sách, item là từng bản sao. Người dùng tìm theo publication, nhưng nghiệp vụ mượn trả phải theo item cụ thể để biết bản sao nào đang available, borrowed hay lost.
```

## 15. Nhóm Mượn Trả: `borrowing_transactions`

### 15.1. Bảng Này Lưu Gì?

`borrowing_transactions` lưu lịch sử mượn/trả.

Nó liên kết:

- User mượn.
- Item được mượn.
- Thủ thư xác nhận mượn.
- Thủ thư xác nhận trả.
- Ngày mượn.
- Hạn trả.
- Ngày trả.
- Trạng thái.

### 15.2. Vì Sao Transaction Liên Kết Với Item, Không Chỉ Publication?

Vì mượn là mượn một bản sao cụ thể.

Ví dụ:

```text
User mượn Clean Code bản barcode CC002
```

Không chỉ là "mượn Clean Code" chung chung.

Trả lời hội đồng:

```text
Transaction liên kết với item vì trạng thái mượn trả thuộc về bản sao cụ thể. Nếu chỉ lưu publication_id, hệ thống không biết bản sao nào đang được giữ bởi người dùng.
```

## 16. Nhóm Đặt Trước: `reservations`

### 16.1. Vấn Đề Thực Tế

Khi sách chưa có bản sao rảnh, người dùng vẫn muốn xếp hàng.

`reservations` lưu:

- User đặt.
- Publication được đặt.
- Item được gán nếu đã có bản sao sẵn.
- Vị trí hàng đợi.
- Hạn giữ sách.
- Trạng thái.

### 16.2. Vì Sao Reservation Liên Kết Với Publication Và Có `assigned_item_id`?

Khi đặt trước, có thể chưa biết bản sao nào sẽ trả về trước.

Vì vậy ban đầu đặt theo publication. Khi có item available, hệ thống gán vào `assigned_item_id`.

Trả lời hội đồng:

```text
Reservation theo publication vì lúc đặt chưa chắc biết bản sao nào sẽ sẵn sàng. Khi có bản sao trả về, hệ thống mới gán assigned_item_id để người dùng đến nhận.
```

## 17. Nhóm Phí Phạt Và Thanh Toán

### 17.1. `fines`

`fines` lưu khoản phạt phát sinh từ một giao dịch mượn.

Ví dụ:

- Trả trễ.
- Mất sách.
- Hỏng sách.

Quan hệ:

```text
borrowing_transactions 1-N fines
```

### 17.2. `fine_payment_orders`

Bảng này lưu đơn thanh toán PayOS.

Một order có thể thanh toán nhiều fine.

Vì vậy cần bảng nối:

```text
fine_payment_order_fines
```

### 17.3. Vì Sao Không Chỉ Lưu `fine_ids` Dạng Text?

Project có thể lưu `fine_ids` như snapshot để hiển thị, nhưng quan hệ chuẩn vẫn nên nằm ở bảng nối.

Trả lời hội đồng:

```text
fine_payment_order_fines là bảng nối chuẩn hóa giữa payment order và fine. Snapshot fine_ids có thể phục vụ hiển thị hoặc trace, nhưng FK trong bảng nối mới giúp database đảm bảo quan hệ đúng.
```

## 18. Nhóm Rating Và Review

### 18.1. `ratings`

`ratings` là review sách, khác với system review.

Nó lưu:

- User đánh giá.
- Publication được đánh giá.
- Số sao.
- Comment.
- Transaction nếu review gắn với lần mượn thật.
- `verified_borrow`.

### 18.2. Vì Sao Rating Có `transaction_id`?

Một user có thể mượn cùng một sách nhiều lần.

Nếu review gắn với transaction, hệ thống biết review đó đến từ lần mượn nào.

Sau migration mới, unique theo `transaction_id` khi có giá trị, thay vì khóa cứng một user chỉ review một sách một lần.

Trả lời hội đồng:

```text
Rating có thể gắn với transaction để chứng minh người dùng đã mượn thật. Điều này giúp review đáng tin hơn và cho phép user đánh giá theo từng lần mượn nếu nghiệp vụ cần.
```

## 20. Nhóm Notification

Notification có hai bảng:

```text
notifications
user_notifications
```

## 27. Transaction Database Là Gì?

### 27.1. Vấn Đề Thực Tế

Khi trả sách, hệ thống có thể phải:

- Cập nhật transaction.
- Cập nhật item.
- Tạo fine nếu trễ.
- Tạo notification.

Nếu làm được bước 1 nhưng lỗi ở bước 2, dữ liệu sai.

### 27.2. ACID

Transaction database giúp đảm bảo ACID:

| Chữ | Ý nghĩa đơn giản |
|---|---|
| A - Atomicity | Thành công hết hoặc rollback hết |
| C - Consistency | Dữ liệu vẫn hợp lệ |
| I - Isolation | Các giao dịch không giẫm lên nhau |
| D - Durability | Commit rồi thì dữ liệu được lưu bền vững |

Trả lời hội đồng:

```text
Database transaction rất quan trọng với mượn trả vì một nghiệp vụ ảnh hưởng nhiều bảng. Nếu có lỗi giữa chừng, rollback giúp tránh trạng thái dữ liệu nửa đúng nửa sai.
```

## 32. Xóa Dữ Liệu Và ON DELETE

### 32.1. Vấn Đề Thực Tế

Nếu xóa một publication, các bảng liên quan xử lý thế nào?

Ví dụ:

- Bản dịch của publication.
- Tag liên kết.
- Review.
- Item.
- Transaction lịch sử.

Không thể xóa bừa vì có thể mất lịch sử mượn trả.

### 32.2. CASCADE, RESTRICT, SET NULL

Các kiểu thường gặp:

| Kiểu | Ý nghĩa |
|---|---|
| CASCADE | Xóa cha thì xóa con |
| RESTRICT | Không cho xóa nếu còn con |
| SET NULL | Xóa cha thì FK con thành null |

Ví dụ:

- Translation có thể `ON DELETE CASCADE` theo publication.
- Fine bị payment order tham chiếu có thể cần restrict.
- Một số librarian reference có thể nullable.

Trả lời hội đồng:

```text
Không phải quan hệ nào cũng cascade. Với dữ liệu lịch sử như mượn trả và thanh toán, cần giữ lại để truy vết. Cascade phù hợp hơn với dữ liệu phụ thuộc như bản dịch hoặc bảng nối.
```

```sql
SELECT p.id, p.title, COUNT(i.id) AS item_count
FROM publications p
LEFT JOIN items i ON i.publication_id = p.id
GROUP BY p.id, p.title
ORDER BY item_count DESC
LIMIT 10;
```

Xem transaction đang mượn:

```sql
SELECT bt.id, u.email, p.title, i.barcode, bt.status, bt.due_date
FROM borrowing_transactions bt
JOIN users u ON u.id = bt.user_id
JOIN items i ON i.id = bt.item_id
JOIN publications p ON p.id = i.publication_id
WHERE bt.status IN ('WAITING_FOR_PICKUP', 'BORROWING', 'OVERDUE')
ORDER BY bt.due_date ASC;
```

Schema được chia theo nhóm: user/role cho tài khoản và phân quyền, catalog cho sách và bản sao, circulation cho mượn trả/đặt trước/phí phạt, recommendation cho wishlist/search/history/user interactions, contact cho phiếu hỗ trợ, notification cho thông báo và AI cho vector/summary/tag.

```text
Thiết kế dùng primary key để định danh bản ghi, foreign key để liên kết bảng, unique/check/not null để bảo vệ dữ liệu. Publication được tách khỏi item vì một đầu sách có nhiều bản sao cụ thể. Các quan hệ nhiều-nhiều như sách-tác giả, sách-tag, user-role dùng bảng nối.

Database được quản lý bằng Flyway migration để mọi môi trường có cùng lịch sử schema. Production cần backup và không được xóa volume tùy tiện. Backend là lớp duy nhất đọc/ghi database sau khi kiểm tra quyền và nghiệp vụ.
```

## 38. Điều Quan Trọng Cần Nhớ

Nếu chỉ nhớ 10 ý, hãy nhớ:

1. Database lưu dữ liệu lâu dài của hệ thống.
2. PostgreSQL phù hợp vì Library74 có nhiều quan hệ dữ liệu.
3. Primary key định danh duy nhất một dòng.
4. Foreign key liên kết bảng và bảo vệ quan hệ.
5. Publication là đầu sách, Item là bản sao cụ thể.
6. Bảng nối dùng cho quan hệ nhiều-nhiều.
7. Constraint giúp dữ liệu không sai.
8. Index giúp truy vấn nhanh nhưng không nên lạm dụng.
9. Flyway quản lý thay đổi schema bằng migration version.
10. Production DB phải backup và không được xóa volume tùy tiện.
